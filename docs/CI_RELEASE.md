# CI and release operations

Windows and Android builds are independent workflows on push to main/master/feature branches, pull requests and manual dispatch. They analyze and test before compiling. Flutter is pinned to 3.47.8 and its verified commit `737ba8f885dc774b53b442759999a312c9461e4e`, Java to 17. GitHub-hosted Windows 2022 includes Visual Studio C++, 7-Zip and Inno Setup 6; a missing compiler fails explicitly. No action workflow has been executed on GitHub during local implementation.

Windows: `pwsh -File tools/bootstrap-windows.ps1`, then `pwsh -File tools/build-windows.ps1`. Resolution uses FLUTTER_ROOT, then PATH, then `.tools/flutter`. Set FFMPEG_BIN to a shared FFmpeg bin directory and INNO_ISCC to ISCC.exe; local installed FFmpeg and `.tools/inno/ISCC.exe` remain fallbacks. `bootstrap-ci-windows.ps1` obtains hash-verified FFmpeg 9.0.2 and libmpv. The payload check requires FFmpeg/FFprobe, accompanying avcodec/avformat/avutil/swresample/swscale DLLs, libmpv, Flutter data and app-local VC runtime. It runs bundled FFmpeg on a synthetic signal. Installer compilation does not launch the installed app or alter user associations.

CI generates original demo media because generated MP4 files are excluded from Git. Windows packaging includes those demo files. Artifacts expire after 14 days and are build results, not a published production release. Each contains build metadata and SHA256SUMS; `python tools/release_integrity.py verify dist` rejects tampering, extra files and unsafe manifest paths. SHA256 verifies integrity, not publisher identity: Windows EXE is currently unsigned Authenticode.

## Android signing

Create and back up a production key using the [Android signing guide](https://developer.android.com/studio/publish/app-signing). Keep the key and passwords out of chat, Git, logs and uploaded artifacts. Configure repository Actions Secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. Base64 is transport encoding, not encryption. CI decodes the key into the runner temporary directory with restricted permissions and removes it on exit. Never replace an existing production key casually; Android update identity depends on it.

For local signed builds set `ANDROID_KEYSTORE_PATH` to the absolute key path plus the three password/alias variables and `TVE_REQUIRE_RELEASE_SIGNING=true`, then `flutter build apk --release --target-platform android-arm64`. Incomplete credentials fail production builds. Without secrets ordinary CI builds `*-TEST-debug.apk`, explicitly identified as test-only; release Gradle no longer silently uses debug signing. CI checks ZIP integrity and `apksigner verify --print-certs`; compare the reported certificate fingerprint with your securely recorded production fingerprint before acceptance. Signing success alone does not establish that the correct publisher key was used.

Only ARM64 libraries are packaged. The app clears Flutter's preconfigured ABI set before setting the ARM64 filter; CI also inspects the APK native ABI directories. Existing app namespace/application ID and Java 17 bytecode target remain stable.

Android export quality is passed to Media3 as a requested H.264 bitrate, constrained to 0.5–50 Mbps. The native bridge validates finite integer requests, uses a resolution/frame-rate-based default for older callers and applies `VideoEncoderSettings` through `DefaultEncoderFactory`. The signatures were checked against the installed Media3 1.11.1 AAR; the final debug package compiled successfully. [Media3 fallback documentation](https://developer.android.com/reference/androidx/media3/transformer/DefaultEncoderFactory.Builder) explains that unsupported device formats may require bitrate/resolution changes. Actual device encoding quality and fallback behavior remain device acceptance checks.

## First publication and release

GitHub CLI is not currently available locally. Install it only if needed using the [official installation instructions](https://github.com/cli/cli#installation); run `gh auth login --web` yourself and check `gh auth status`. Never paste tokens/passwords into chat. Verify the intended owner and existing `tiger-video-edit` repository before creating a new public repository. Do not upload source until publication review and owner confirmation are complete.

Configure a GitHub environment named `release` with required reviewers and prevent self-review where the account plan supports it. Restrict deployment tags. Without environment protection, its name alone provides no approval barrier. After owner approval, license review and real device acceptance, set repository variables `PUBLICATION_APPROVED`, `LICENSE_REVIEW_APPROVED`, `DEVICE_ACCEPTANCE_APPROVED` to literal `true`. These are explicit external acceptance records; leave unset while gates are open.

The separate Approved Release workflow accepts `vMAJOR.MINOR.PATCH` tags or manual dispatch naming an existing tag pointing at the selected workflow commit. It checks tag/version equality, gates and full history secrets, runs both builds, refuses test APKs, re-verifies manifests and creates a release only after protected environment approval. Ordinary pushes never create releases. Set up the environment before pushing any release tag. Prepare `docs/RELEASE_NOTES_3.0.md` with changes and known issues before running it. Subsequent versions must select their matching release notes file before publishing.

Do not infer identical binaries from identical app versions.

Actions use supported v4 artifact APIs with explicit missing-file failure ([upload-artifact documentation](https://github.com/actions/upload-artifact)). GitHub environment protection is configured outside YAML ([GitHub documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)). Before distribution review the [FFmpeg redistribution requirements](https://www.ffmpeg.org/legal.html), exact mpv dependency source and notices, and [Inno licensing](https://jrsoftware.org/isinfo.php). Local Inno 7.1.1 identifies as non-commercial-use-only; CI's preinstalled Inno 6 and any replacement compiler require their own license verification. No commercial tool license was purchased or selected automatically.
